# Процесс создания профиля судна по документации

## Цель
Пользователь не должен перепечатывать характеристики, уже содержащиеся в судовых документах. Создание профиля строится вокруг загрузки источников и проверки извлечённых кандидатов.

## Целевой сценарий
1. Пользователь создаёт черновик судна; название и тип могут быть извлечены из документа.
2. Загружает Ship Particulars, Stability Booklet, General Arrangement, Lines Plan и другие относящиеся к судну файлы.
3. Система сохраняет оригинал неизменным, вычисляет SHA-256, фиксирует имя, MIME-тип, размер, дату загрузки и связь с судном.
4. Извлекатель формирует кандидаты: название, тип, LOA, LBP, moulded breadth (B), moulded depth (D), начало координат, вертикальный datum/baseline, направления X/Y/Z.
5. Каждый кандидат содержит источник: документ, страницу, таблицу/раздел и фрагмент текста. Без точной ссылки кандидат не может быть подтверждён.
6. Кандидаты из разных документов сопоставляются. Несовпадения показываются рядом; автоматический выбор «самого вероятного» значения запрещён.
7. Пользователь подтверждает, исправляет или отклоняет каждый кандидат. Подтверждение создаёт новую версию данных судна и сохраняет время решения.
8. Не найденные поля остаются незаполненными. Никаких предположений об AP, baseline или направлениях осей.

## Статусы
- NOT_FOUND — кандидат не обнаружен.
- EXTRACTED — кандидат извлечён, но не проверен.
- CONFLICT — источники содержат несовпадающие значения.
- REVIEWED — человек сверил значение с оригиналом.
- APPROVED_DATA — значение принято в конкретную версию исходных данных судна.
- REJECTED — кандидат отклонён.

EXTRACTED и REVIEWED не означают эксплуатационное одобрение всего профиля.

## Обработка файлов
- Оригиналы хранятся отдельно от публичной директории frontend.
- Разрешённые типы и максимальный размер задаются конфигурацией; расширение файла не считается достаточной проверкой типа.
- SHA-256 используется для контроля целостности и выявления повторной загрузки.
- Оригинал не перезаписывается при повторной загрузке или новой редакции документа.
- Удаление/замена источника не должно незаметно менять ранее созданные версии данных.

## Извлечение и ограничения
- Текстовые PDF могут обрабатываться программным извлечением текста.
- Сканированные PDF и изображения требуют OCR; до подключения OCR они получают статус «Требуется OCR», а не считаются пустыми документами.
- OCR/LLM и регулярные выражения формируют только кандидаты.
- Числа без однозначной единицы измерения, datum или контекста не принимаются автоматически.
- Единицы нормализуются только при однозначном преобразовании; исходное написание сохраняется.
- Значения из разных редакций документов не смешиваются без явного решения пользователя.

## Проверки
- Тесты на варианты LOA/L.O.A., LBP/L.B.P., moulded breadth и moulded depth.
- Проверка десятичной запятой/точки и явных единиц.
- Негативные тесты на неоднозначные числа, отсутствие единиц, конфликт документов и неверный диапазон.
- Тесты SHA-256 и ограничений размера/типа файла.
- Для координатных соглашений обязателен контекст документа; направления осей нельзя выводить только из распространённой практики.

## Граница безопасности
Пока кандидат не проверен и не включён в утверждённую версию данных, он не может участвовать в расчётном процессе. Даже утверждённые данные в разработческой версии ShipLoad не означают, что приложение одобрено для эксплуатации или заменяет судовой Loadicator.

## Проверка извлечённых кандидатов (реализовано частично)

Извлечённые размерения LOA, LBP, moulded breadth и moulded depth остаются кандидатами до явного решения проверяющего. Для каждого кандидата интерфейс показывает исходное значение, единицу, страницу и совпавший фрагмент PDF. Оригинал доступен по ссылке из карточки документа.

Проверяющий может:
- подтвердить найденное значение;
- скорректировать значение в метрах и подтвердить исправленный вариант;
- отклонить кандидата, оставив комментарий через API (поле комментария поддерживается сервером).

Решение записывается в отдельную append-only таблицу `document_candidate_decisions`. Повторное решение по тому же индексу кандидата блокируется. Запись хранит исходное и принятое значения, поле, единицу, страницу, исходный текст, метку проверяющего и время.

Подтверждение создаёт новую запись в `vessel_data_revisions`. Каждая ревизия содержит полный JSON-снимок известных и подтверждённых значений, ссылки на источники для каждого параметра, номер ревизии, метку автора и краткое описание изменения. Ранее созданные ревизии не обновляются. API чтения: `GET /api/v1/vessels/{vessel_id}/data-revisions`.

Решение не перезаписывает поля чернового профиля `vessels`. Это сделано намеренно: ревизии с provenance — отдельная история подтверждённых исходных данных. Координатная система, начало координат AP, baseline/datum и направления X/Y/Z не извлекаются и не утверждаются этим механизмом.

**Ограничения текущей реализации:** метка проверяющего вводится вручную и не является подтверждённой личностью; аутентификация, электронная подпись и разграничение ролей отсутствуют. Решение подтверждает только конкретный кандидат и не делает весь профиль судна готовым для расчётов или эксплуатации. Перед подключением расчётного ядра потребуются отдельная проверка полного комплекта данных, правил совместимости ревизий и контроль доступа.
